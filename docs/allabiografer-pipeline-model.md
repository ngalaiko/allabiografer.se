# Schema.org pipeline results

Use [`Dataset`](https://schema.org/Dataset) for each saved result. Parse and merge already use it. A fetch dataset can link selected cinemas with [`about`](https://schema.org/about) and list captured files as [`DataDownload`](https://schema.org/DataDownload) distributions when they are available to consumers. Each distribution has a [`contentUrl`](https://schema.org/contentUrl) and [`encodingFormat`](https://schema.org/encodingFormat); the captured bytes stay unchanged. Keep the existing `mainEntity` → [`ItemList`](https://schema.org/ItemList) for parsed or merged entity references. Link each result to its input datasets with [`isBasedOn`](https://schema.org/isBasedOn).

A run is separate from what it produced. If execution records are needed, use [`DownloadAction`](https://schema.org/DownloadAction) for fetch and [`CreateAction`](https://schema.org/CreateAction) for parse and merge. Use [`object`](https://schema.org/object) for the inputs, [`result`](https://schema.org/result) for the output dataset, and [`actionStatus`](https://schema.org/actionStatus) for success or failure. A failed action can link an [`Error`](https://schema.org/Error) through [`error`](https://schema.org/error); `Error` is in Schema.org’s new-terms area. [`SoftwareSourceCode`](https://schema.org/SoftwareSourceCode) can describe an adapter, linked from the run via [`instrument`](https://schema.org/instrument).

Start with datasets for all three stages. Keep fetch’s frozen routing in `selection.json`: `about` identifies the cinemas, but it does not specify which adapter and venue ID to replay. Add action records only if consumers need run status or timing.
